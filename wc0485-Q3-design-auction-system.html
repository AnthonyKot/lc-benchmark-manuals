Problem Statement

Implement an AuctionSystem class that tracks bids in real time. A bid is keyed by userId and itemId, and stores a positive bid amount.

  • AuctionSystem(): initialize the object.
  • addBid(userId, itemId, bidAmount): add a bid; if the same user already has a bid on the same item, replace it.
  • updateBid(userId, itemId, newAmount): update an existing bid. The bid is guaranteed to exist.
  • removeBid(userId, itemId): remove an existing bid. The bid is guaranteed to exist.
  • getHighestBidder(itemId): return the user with the highest bid on that item; ties go to the highest userId. Return -1 if the item has no active bids.

Constraints: 1 <= userId, itemId <= 5 * 10^4, 1 <= bidAmount, newAmount <= 10^9, and at most 5 * 10^4 total operation calls.

Problem Essence

The object needs two views of the same active bids: a direct lookup for the current amount of a user's bid on an item, and a per-item structure that can expose the maximum (bidAmount, userId) pair. The ordering key is exactly (amount ascending, userId ascending) if you read the maximum, or the equivalent descending comparator if you read the first element.

Invariant: for every active bid (itemId, userId, amount), the current-bid map must agree with the candidate structure used by getHighestBidder. Ordered-set solutions maintain this eagerly; heap solutions restore it lazily when querying.

The local statement contains one official example. Additional edge cases to rehearse are:

  • Replacement through addBid: addBid(7, 9, 10), addBid(7, 9, 3); user 7's active amount is now 3, not both amounts.
  • Empty after removal: after removing the last active bid for an item, getHighestBidder must return -1.

Decision Rule / Algorithm

Ordered-set version

  1. Keep bids[itemId][userId] = amount.
  2. Keep ordered[itemId] as a sorted set of pairs (amount, userId).
  3. On addBid, if an old amount exists, remove (oldAmount, userId), then insert the new pair.
  4. On updateBid, remove the old pair and insert (newAmount, userId).
  5. On removeBid, remove the pair from the set and delete the user from the map.
  6. On getHighestBidder, return the userId from the largest pair, or -1 if the set is missing or empty.

Complexity is O(log k) for modifications and O(1) or O(log k) to fetch the maximum depending on the language API, where k is the number of active bids for the item.

Lazy-heap version

  1. Keep the same current-bid map.
  2. For each item, push every new candidate onto a max-heap ordered by (amount, userId).
  3. Do not remove stale heap entries during update or removal.
  4. On getHighestBidder, repeatedly pop the heap top while it no longer matches the current-bid map.
  5. Return the first valid top, or -1 if none remains.

Each stale heap entry is popped at most once, so total heap cleanup is amortized. This is the dominant family among the Python and JavaScript accepted files.

Implementation Skeleton

class AuctionSystem:
    def __init__(self):
        self.amount = {}   # itemId -> {userId: bidAmount}
        self.heap = {}     # itemId -> [(-bidAmount, -userId)]

    def addBid(self, userId, itemId, bidAmount):
        self.amount.setdefault(itemId, {})[userId] = bidAmount
        self.heap.setdefault(itemId, [])
        heappush(self.heap[itemId], (-bidAmount, -userId))

    def updateBid(self, userId, itemId, newAmount):
        self.amount[itemId][userId] = newAmount
        heappush(self.heap[itemId], (-newAmount, -userId))

    def removeBid(self, userId, itemId):
        del self.amount[itemId][userId]

    def getHighestBidder(self, itemId):
        if itemId not in self.heap:
            return -1
        while self.heap[itemId]:
            neg_amount, neg_user = self.heap[itemId][0]
            amount, userId = -neg_amount, -neg_user
            if self.amount.get(itemId, {}).get(userId) == amount:
                return userId
            heappop(self.heap[itemId])
        return -1

For ordered-set languages, replace the heap with a set/tree keyed by (amount, userId) and remove old pairs eagerly before inserting replacements.

Reimplementation Checklist

  • Represent each active bid exactly once in the current-bid map.
  • Apply the tie rule by including userId in the max key, not by scanning users later.
  • Handle addBid as replacement when the user already bid on the item.
  • Trust the validity guarantees for updateBid and removeBid, but still update both structures consistently.
  • Return -1 when the item is absent or all candidates have been removed.
  • Use integer-safe comparators; amounts fit in 32-bit signed integers, but direct subtraction comparators are still less robust than explicit comparisons.

Wrong But Tempting

  • Keeping only a max amount per item. This loses the user id and breaks updates/removals.
  • Sorting all bids inside every getHighestBidder. That can be O(k log k) per query and risks TLE.
  • Using a heap without stale-entry validation. Removed or outdated bids can remain at the top.
  • Breaking ties by smaller userId. The statement requires the highest userId.
  • Forgetting that addBid replaces an existing bid by the same user on the same item.
  • Using only userId as a global key. The same user can bid on multiple items independently.

Failure Patterns From Stats

Failed submission status counts in stats.json: 2 Wrong Answer, 4 Runtime Error, 3 Time Limit Exceeded, and 1 Compile Error.

  • Wrong Answer: commonly caused by incorrect tie-breaking, stale heap tops, or not replacing an existing bid in addBid.
  • Runtime Error: likely from assuming an item structure exists in getHighestBidder or dereferencing an empty heap/set after removals.
  • Time Limit Exceeded: likely from rescanning or resorting all bids per query instead of maintaining a heap/tree.
  • Compile Error: comparator or mutable-reference mistakes are easy in Java, C++, and Rust when storing custom bid objects in ordered sets.
