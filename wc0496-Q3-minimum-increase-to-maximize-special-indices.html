Problem Statement

You are given an integer array nums of length n. An index i, where 0 < i < n - 1, is special if nums[i] > nums[i - 1] and nums[i] > nums[i + 1].

One operation chooses any index and increases nums[i] by 1. Return the minimum number of operations needed after first maximizing the number of special indices.

Constraints: 3 <= n <= 100000, 1 <= nums[i] <= 1000000000.

Problem Essence

Only interior positions 1..n-2 can be special. If index i is chosen to be special, it only needs to be raised to strictly exceed its two original neighbors, so its independent cost is:

cost[i] = max(0, max(nums[i - 1], nums[i + 1]) + 1 - nums[i])

Two adjacent indices cannot both be special, because nums[i] > nums[i+1] and nums[i+1] > nums[i] cannot both hold. Therefore the maximum number of special indices is the maximum size of a non-adjacent subset of the n - 2 interior positions. Among all such maximum-size subsets, minimize the sum of the selected costs.

Worked Example

For nums = [5,2,1,4,3], the interior positions are 1, 2, and 3.

IndexNeighborsTarget valueCurrentCost
15 and 1624
22 and 4514
31 and 3440

With three interior positions, the maximum non-adjacent count is 2, and the only way to take two positions is indices 1 and 3. Their total cost is 4 + 0 = 4. Raising index 1 from 2 to 6 makes indices 1 and 3 special, so the answer is 4.

Decision Rule / Algorithm

Use dynamic programming over interior positions. Store a pair (count, cost) meaning the best result up to the current interior position: larger count is always better; for equal count, smaller cost is better.

  1. Initialize dp[i-2] = (0, 0) and dp[i-1] = (0, 0).
  2. For each interior index i from 1 to n - 2, compute cost.
  3. Option A skips i: use the previous pair.
  4. Option B takes i: use the pair from two positions back plus (1, cost).
  5. Pick the better pair by count first, cost second.
  6. Return the cost from the final pair.

Several accepted solutions exploit the fact that the maximum count is fixed by parity and use a cost-only recurrence. The pair recurrence is less error-prone and still O(n) time and O(1) memory.

Implementation Skeleton

def minIncrease(nums):
    n = len(nums)
    prev2_count, prev2_cost = 0, 0
    prev1_count, prev1_cost = 0, 0

    for i in range(1, n - 1):
        cost = max(0, max(nums[i - 1], nums[i + 1]) + 1 - nums[i])

        skip_count, skip_cost = prev1_count, prev1_cost
        take_count, take_cost = prev2_count + 1, prev2_cost + cost

        if take_count > skip_count or (take_count == skip_count and take_cost < skip_cost):
            cur_count, cur_cost = take_count, take_cost
        else:
            cur_count, cur_cost = skip_count, skip_cost

        prev2_count, prev2_cost = prev1_count, prev1_cost
        prev1_count, prev1_cost = cur_count, cur_cost

    return prev1_cost

Reimplementation Checklist

  • Iterate only over interior indices 1 through n - 2.
  • Use max(nums[i - 1], nums[i + 1]) + 1 as the required target for a chosen peak.
  • Clamp each cost at zero; already-special indices cost nothing.
  • For a chosen index, transition from i - 2, never i - 1.
  • Compare DP states by maximum special count first, then minimum cost.
  • Use 64-bit integer totals in Java, C++, Go, Rust, and similar languages because costs can sum beyond 32-bit limits.
  • Return the minimum cost associated with the maximum achievable count, not the maximum count itself.

Wrong But Tempting

  • Choosing every locally cheap interior index greedily can miss the maximum-count tie structure.
  • Sorting positions by cost is invalid because adjacency is positional.
  • Trying to modify neighbors downward is impossible; operations only increase values.
  • Letting adjacent chosen peaks coexist is logically impossible, regardless of how much either value is increased.
  • Minimizing cost without tracking or enforcing maximum count may choose too few special indices.
  • Using 32-bit totals can overflow: up to about 50000 * 1000000000 operations may be needed.
