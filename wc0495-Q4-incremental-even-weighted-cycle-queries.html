Incremental Even-Weighted Cycle Queries

Problem Statement

You are given n nodes labeled 0 to n - 1 and an initially empty undirected graph. Each input edge is [u, v, w], where w is either 0 or 1. Process edges in order. Add an edge only if, after adding it, every cycle in the graph has an even total edge weight. Return the number of edges successfully added.

Constraints include 3 <= n <= 5 * 10^4, 1 <= edges.length <= 5 * 10^4, distinct edges, 0 <= u < v < n, and binary weights.

Problem Essence

The graph can contain cycles, but only cycles whose XOR/sum parity is even. Assign each node a hidden bit. An edge of weight 0 says its endpoints must have the same bit; an edge of weight 1 says its endpoints must have different bits. An edge is addable exactly when this parity constraint is consistent with all previously accepted constraints.

That turns the problem into online bipartite-style parity constraints, solved with disjoint set union that stores each node's XOR parity to its component root.

Worked Example

Input: n = 3, edges = [[0,1,1],[1,2,1],[0,2,1]]

  1. Add [0,1,1]: nodes 0 and 1 become connected with different bits. Count is 1.
  2. Add [1,2,1]: node 2 joins; 1 and 2 must differ. Now the implied parity between 0 and 2 is 1 XOR 1 = 0. Count is 2.
  3. Check [0,2,1]: the existing parity between 0 and 2 is 0, but the edge requires 1. Adding it would make cycle 0-1-2-0 have odd weight 1 + 1 + 1 = 3. Reject it.

Output: 2

Other Official Examples

Example 2: n = 3, edges = [[0,1,1],[1,2,1],[0,2,0]], expected output 3.

After accepting the first two edges, the path parity between 0 and 2 is 0. The third edge has weight 0, so it agrees with the existing path and creates an even-weighted cycle with total 2.

Decision Rule / Algorithm

Maintain arrays parent, rank or size, and parity. Here parity[x] is the XOR of edge weights from x to parent[x]; after path compression it becomes the XOR from x to the root.

  1. For edge (u, v, w), run find(u) and find(v), updating compressed parities.
  2. If roots are equal, the edge is accepted only when parity[u] XOR parity[v] == w.
  3. If roots differ, merge the two components and set the attached root's parity so the new relation holds: parity[attachedRoot] = parity[u] XOR parity[v] XOR w, with endpoint values interpreted after find.
  4. Increment the answer for every accepted edge, including redundant edges that are consistent within an existing component.

Time complexity is O((n + m) alpha(n)), effectively linear for m = edges.length. Space complexity is O(n).

Implementation Skeleton

def numberOfEdgesAdded(n, edges):
    parent = [0, 1, 2, ..., n - 1]
    rank = [0] * n
    parity = [0] * n

    def find(x):
        if parent[x] != x:
            old_parent = parent[x]
            root = find(old_parent)
            parity[x] ^= parity[old_parent]
            parent[x] = root
        return parent[x]

    ans = 0
    for u, v, w in edges:
        ru = find(u)
        rv = find(v)

        if ru == rv:
            if (parity[u] ^ parity[v]) == w:
                ans += 1
        else:
            if rank[ru] < rank[rv]:
                # attach ru under rv
                parent[ru] = rv
                parity[ru] = parity[u] ^ parity[v] ^ w
            else:
                # attach rv under ru
                parent[rv] = ru
                parity[rv] = parity[u] ^ parity[v] ^ w
                if rank[ru] == rank[rv]:
                    rank[ru] += 1
            ans += 1

    return ans

If you swap roots before attaching, also keep the endpoint parity values consistent. Several accepted C++/Java variants store xu = parity[u] and xv = parity[v] immediately after find before union.

Reimplementation Checklist

  • Initialize every node as its own parent and every parity as 0.
  • In find, save the old parent before recursion; use that saved index to update parity during path compression.
  • Call find(u) and find(v) before reading final parity[u] and parity[v].
  • Accept consistent redundant edges inside the same component; do not merge or reject them automatically.
  • Reject only contradictions where existing endpoint parity differs from the new weight.
  • Use iterative find in languages where recursion depth is a concern, or rely on union by rank plus compression.

Wrong But Tempting

  • Plain DSU without parity: it only knows connectivity, not whether the existing path has odd or even weight.
  • Reject every cycle edge: the task allows cycles as long as their total weight is even.
  • Track total component weight: cycle validity depends on parity between the two endpoints, not a component aggregate.
  • Use BFS/DFS for every edge: it can find path parity but costs up to O(m(n+m)), too slow for 5 * 10^4.
  • Forget parity update on path compression: this silently corrupts later comparisons.

Accepted Algorithm Families

Recursive parity DSU. Most Python, Java, JavaScript, C++, Rust, and TypeScript submissions use recursive find with path compression and a parity/diff/xorToParent array.

Iterative parity DSU. Some Go implementations avoid recursion by collecting the path and then compressing it while updating XOR distances.

Rank/size variants. Accepted code uses rank, size, or direct root attachment. All are valid when the attached root parity is set from parity[u] XOR parity[v] XOR w.
