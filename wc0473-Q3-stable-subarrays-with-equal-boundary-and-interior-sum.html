Stable Subarrays With Equal Boundary and Interior Sum

Problem id: wc0473-Q3-stable-subarrays-with-equal-boundary-and-interior-sum

Provenance

Generated from the local files problem.md, stats.json, and the eight accepted__* submissions in this directory. The source problem is a LeetCode Medium problem named Stable Subarrays With Equal Boundary and Interior Sum with function countStableSubarrays(capacity).

Problem Statement

Given an integer array capacity, count subarrays capacity[l..r] whose length is at least three and whose first and last elements both equal the sum of all elements strictly between them: 

capacity[l] = capacity[r] = capacity[l + 1] + ... + capacity[r - 1]

Constraints: 3 <= capacity.length <= 100000 and -1000000000 <= capacity[i] <= 1000000000. Because sums can exceed 32-bit range, prefix sums and the answer should be stored in 64-bit integer types where the language has fixed-width integers.

Problem Essence

The task is not to enumerate all subarrays. It is to turn the interior-sum condition into a lookup over previous left endpoints. Let pref[i] be the sum of elements before index i. For a right endpoint r, a valid left endpoint l must satisfy: 

r - l + 1 >= 3
capacity[l] == capacity[r]
pref[r] - pref[l + 1] == capacity[r]

Since pref[l + 1] = pref[l] + capacity[l] and capacity[l] = capacity[r], this becomes pref[l] == pref[r] - 2 * capacity[r]. Count prior left endpoints by the pair (capacity[l], pref[l]).

Worked Example

Input: [9, 3, 3, 3, 9]

Output: 2

The full subarray [9,3,3,3,9] is stable because the interior sum is 3 + 3 + 3 = 9. The middle subarray [3,3,3] is also stable because its single interior element is 3. No other length-at-least-three subarray has both equal boundaries and matching interior sum.

Other Official Examples

InputExpectedReason
[1,2,3,4,5] 0 No length-at-least-three subarray has equal first and last elements.
[-4,4,0,0,-8,-4] 1 The whole array works because 4 + 0 + 0 + (-8) = -4.

Decision Rule / Algorithm

  1. Build or stream prefix sums with pref[0] = 0 and pref[i + 1] = pref[i] + capacity[i].
  2. Maintain a frequency map keyed by (value, prefixBeforeLeft).
  3. When processing right endpoint r, only left endpoints up to r - 2 may be inserted; this enforces length at least three.
  4. For each r, query (capacity[r], pref[r] - 2 * capacity[r]) and add that frequency to the answer.
  5. Return the accumulated count.

Equivalent accepted submissions also scan from right to left. In that form, they store candidate right endpoints by (capacity[r], pref[r]) and query with a transformed left-side expression such as pref[l] + 2 * capacity[l]. The invariant is the same: one hash lookup represents the boundary equality and the interior sum equation.

Implementation Skeleton

long countStableSubarrays(int[] capacity) {
    int n = capacity.length;
    long[] pref = new long[n + 1];
    for (int i = 0; i < n; i++) {
        pref[i + 1] = pref[i] + capacity[i];
    }

    Map<Pair(value, prefix), count> seen = new HashMap<>();
    long ans = 0;

    for (int r = 0; r < n; r++) {
        int l = r - 2;
        if (l >= 0) {
            seen[(capacity[l], pref[l])] += 1;
        }

        long targetPrefix = pref[r] - 2L * capacity[r];
        ans += seen.getOrDefault((capacity[r], targetPrefix), 0);
    }

    return ans;
}

Reimplementation Checklist

  • Use prefix sums over elements before an index, not through the index, and be consistent.
  • Insert index r - 2 before querying r; this admits length exactly three but excludes length one and two.
  • Require equal boundary values by including capacity[index] in the hash key.
  • Use 64-bit arithmetic for prefix sums and 2 * capacity[r].
  • Return a 64-bit count in Java, Go, C++, C#, Kotlin, Scala, and Rust.
  • Keep the algorithm O(n) time and O(n) memory; nested loops will not pass for n = 100000.

Wrong But Tempting

  • Checking every l, r pair with prefix sums. This is still O(n^2).
  • Using only equal boundary values and forgetting the prefix-sum target.
  • Storing pref[l + 1] but querying as if the map stored pref[l], or the reverse.
  • Adding the current right endpoint to the map too early, which creates invalid length-one or length-two matches.
  • Using 32-bit sums in Java, Go, or C++ when 100000 * 1000000000 is possible.
  • Assuming negative values break the method; the prefix-sum equation works with negative, zero, and positive values.

Language and Performance Notes

The concrete accepted runs in stats.json.performance_by_language show all accepted languages using linear hash-map solutions:

  • Java has five accepted submissions. Fastest: 71 ms from set2-qwen3.5-cloud-t0.0-java; slowest: 94 ms. Memory ranged from 132.9 MB to 144.7 MB.
  • Go has one accepted submission at 106 ms and 19.1 MB, the lowest memory reported among the accepted set.
  • JavaScript has one accepted submission at 117 ms and 94.1 MB. Using nested Map objects keeps composite keys simple.
  • Python 3 has one accepted submission at 311 ms and 42.8 MB. It still passes with dictionaries because the algorithm is O(n), but it is noticeably slower than the compiled/runtime-JIT entries.

For Java, a custom immutable key class or nested Map<Integer, Map<Long, Integer>> both appeared in accepted solutions. For JavaScript, ordinary numbers are safe here because the maximum prefix magnitude is about 1e14, below Number.MAX_SAFE_INTEGER.
