Problem Statement

You are given an integer array nums and an integer k.

For any non-empty subarray nums[l..r], define its cost as:

cost = (max(nums[l..r]) - min(nums[l..r])) * (r - l + 1)

Return the number of subarrays whose cost is less than or equal to k.

Constraints: 1 <= nums.length <= 100000, 1 <= nums[i] <= 1000000000, 0 <= k <= 1000000000000000.

Problem Essence

The key observation is monotonicity by window inclusion: if a fixed window is invalid, extending it cannot make its length smaller, and its max-min range cannot decrease below the range of the original window. So for each right endpoint, there is a smallest valid left boundary after shrinking.

Maintain the current window max and min in O(1) amortized time using two monotonic deques of indices. Once the current window is valid, every suffix of it ending at the current right index is also valid, so add right - left + 1.

Worked Example

Decision Rule / Algorithm

  1. Scan right from 0 to n - 1.
  2. Push right into a decreasing deque for maximums, popping smaller or equal trailing values.
  3. Push right into an increasing deque for minimums, popping larger or equal trailing values.
  4. While (nums[maxDeque.front] - nums[minDeque.front]) * (right - left + 1) > k, move left rightward and discard expired deque fronts.
  5. Add right - left + 1 to the answer.

Each index is inserted and removed at most once from each deque, so the time complexity is O(n) and the auxiliary space is O(n) in the worst case.

Implementation Skeleton

def countSubarrays(nums, k):
    left = 0
    answer = 0
    maxdq = deque()  # indices, nums values decreasing
    mindq = deque()  # indices, nums values increasing

    for right, value in enumerate(nums):
        while maxdq and nums[maxdq[-1]] <= value:
            maxdq.pop()
        maxdq.append(right)

        while mindq and nums[mindq[-1]] >= value:
            mindq.pop()
        mindq.append(right)

        while (nums[maxdq[0]] - nums[mindq[0]]) * (right - left + 1) > k:
            left += 1
            while maxdq and maxdq[0] < left:
                maxdq.popleft()
            while mindq and mindq[0] < left:
                mindq.popleft()

        answer += right - left + 1

    return answer

Reimplementation Checklist

  • Use indices in both deques, not raw values, so expired elements can be removed.
  • Use 64-bit arithmetic for the cost and result. The answer can be about n * (n + 1) / 2, and k reaches 10^15.
  • After moving left, remove all deque fronts with index less than left.
  • Count subarrays after the while loop has restored validity.
  • Equal-value popping is fine and common: <= for the max deque and >= for the min deque keeps the newest duplicate.

Wrong But Tempting

  • Checking every subarray and recomputing max/min is O(n^3), or O(n^2) with incremental extrema, and will not survive n = 100000.
  • Using a single deque cannot track both max and min; the cost needs their difference.
  • Shrinking only once when the cost is too high is insufficient. A single large range can require many left moves.
  • Counting right - left instead of right - left + 1 drops the one-element suffix.
  • Using 32-bit int for (max - min) * length can overflow even when the final comparison is with a long value.

Accepted Algorithm Families

Right-expanding sliding window

Most accepted files use the standard loop over right, maintain min/max deques, shrink left while invalid, and add valid suffix count. This appears in Python, Java, C++, Go, JavaScript, and TypeScript submissions.

Left-anchored two pointer

The Rust accepted solution advances right as far as possible for each left, counts right - left, and then expires the outgoing left index. It is the same monotonic-deque invariant expressed from the other side.

Deque implementation variants

Java accepted files often use fixed integer arrays plus head/tail pointers for lower overhead. Python uses collections.deque; C++ and Rust use standard deque structures.

Failure Patterns From Stats

stats.json records one failed submission status: Time Limit Exceeded. That aligns with the main risk for this problem: any O(n log n) with heavy constants might pass depending on implementation, but O(n^2) enumeration is structurally wrong for n = 100000.

  • Avoid nested loops over all starts and ends.
  • Avoid recomputing max and min from scratch after each left movement.
  • Avoid JavaScript/TypeScript Array.shift() in the hot path; it can make queue operations linear.
