Problem Statement

You are given two integer arrays of size 2: d = [d1, d2] and r = [r1, r2].

Two delivery drones must complete deliveries. Drone i must complete exactly di deliveries. Each delivery takes exactly one hour, and only one drone can make a delivery in any hour.

Drone i cannot deliver at hours that are multiples of ri, because it must recharge then. Return the minimum total number of hours needed to complete all deliveries.

Constraints: 1 <= di <= 10^9, 2 <= ri <= 3 * 10^4, and both arrays have length 2.

Problem Essence

For a guessed finishing time T, count which hours from 1..T can be used by each drone. The answer is the smallest T for which there are enough non-recharge hours for drone 1, enough for drone 2, and enough total hours where at least one drone is available.

The key is that this feasibility check is monotonic: if time T works, any larger time also works. That makes binary search the natural outer algorithm.

Decision Rule / Algorithm

Let L = lcm(r1, r2). For a candidate time T:

  • Drone 1 has T - floor(T / r1) available hours.
  • Drone 2 has T - floor(T / r2) available hours.
  • The total number of hours where at least one drone is available is T - floor(T / L), because only multiples of L are blocked for both drones.

The compact accepted predicate is:

can(T) =
    d1 <= T - T / r1
    and d2 <= T - T / r2
    and d1 + d2 <= T - T / lcm(r1, r2)

This is enough because each hour can host at most one delivery. The first two inequalities prevent either drone from being individually starved; the third prevents the combined schedule from requiring hours where both drones are recharging.

The expanded form seen in one Java and one Python accepted solution computes:

bothAvailable = T - T/r1 - T/r2 + T/L
onlyDrone1    = T/r2 - T/L
onlyDrone2    = T/r1 - T/L
needShared1   = max(0, d1 - onlyDrone1)
needShared2   = max(0, d2 - onlyDrone2)
can(T)        = needShared1 + needShared2 <= bothAvailable

It is more verbose but useful when explaining the allocation of exclusive and shared hours.

Implementation Skeleton

function minimumTime(d, r):
    d1, d2 = d[0], d[1]
    r1, r2 = r[0], r[1]
    L = lcm(r1, r2)

    function can(T):
        return d1 <= T - floor(T / r1)
           and d2 <= T - floor(T / r2)
           and d1 + d2 <= T - floor(T / L)

    low = 0
    high = 1
    while not can(high):
        high *= 2

    while low < high:
        mid = floor((low + high) / 2)
        if can(mid):
            high = mid
        else:
            low = mid + 1

    return low

Use 64-bit integer arithmetic for T, d1 + d2, and lcm. In JavaScript, ordinary Number is safe here because the values are well below 2^53.

Reimplementation Checklist

  • Read d[0], d[1], r[0], and r[1].
  • Compute gcd with Euclid's algorithm.
  • Compute lcm as r1 / gcd(r1, r2) * r2 to avoid unnecessary overflow.
  • Write a monotonic can(T) predicate using the three inequalities above.
  • Binary search the first feasible T.
  • Use long, long long, int64, or Python int for time and counts.
  • Return the lower bound after the search converges.

Wrong But Tempting

  • Greedy simulation hour by hour: impossible at di up to 10^9.
  • Only checking d1 + d2 <= T: ignores hours where both drones recharge.
  • Only checking individual availability: misses conflicts where both drones need the same shared hours.
  • Counting shared hours as unavailable: a shared hour is usable by either drone, just not by both at once.
  • Using r1 * r2 as lcm without gcd: overcounts the both-recharging interval when recharge rates share a factor.
  • 32-bit arithmetic: the answer can be around billions, and intermediate bounds can be larger.

Both accepted families are mathematically equivalent. The compact three-inequality predicate is shorter and less error-prone for reimplementation.
